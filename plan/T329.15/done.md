Data half of T329 §8b. Every graph tool call (`symbol`, `callers`, `impact`, `outline`, `explore`) in any rtok process (MCP server, `rtok mcp --call`) appends a start, a progress (scope resolved) and an end event to a new append-only `graph_events` table (migration `0040_graph_events`, capped to the newest 5000 rows on insert, free text clipped to 200 characters). `rtok dashboard` reads them with an id cursor (`id > last`, one primary-key range scan every 250 ms, never the calls table) and pushes `{"type":"calls","batch":...}` frames to sockets that sent `{"calls":{"subscribe":true}}`. The poller starts with the first subscriber and stops with the last. A batch lists at most 100 events (a call's start and progress are dropped when its end is in the batch), counts the rest in `omitted`, and its `summary` (starts, ends, failed, est_before, est_after) counts every event, so a 500-call burst arrives in at most four small frames per second and totals never undercount. The end event copies the call's `graph` `measurements` rows (read between the measurement head at the start and the end), so the numbers are the rows `rtok stats --plugin graph` sums. No replay: the subscription ack is an empty batch whose `head` is the newest event id; a reconnect or a restarted server starts from the head again. The store part is `crates/rtok-store/src/graph_events.rs` (Diesel only), the writer is `src/plugins/graph/events.rs` (`Call`, every write fail open and off the hook path), the reader is `src/web/live.rs`; the protocol adds `ServerFrame::Calls` and `ClientMessage::Calls`, and `ws.schema.json`, `snapshot.gen.ts`, a `parseFrame` case and a no-op handler in `sample.ts` are regenerated or added. Documented in `docs/commands.md` and its ru and uk copies.
