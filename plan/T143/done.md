Bug: `src/hooks/mod.rs`'s `dispatch` calls `otel::export::spawn_child` on every `Stop`/`SessionEnd` hook when OTel is configured. `spawn_child` spawns a detached, never-waited `<exe> otel flush`, and `flush`'s exclusive `flock` (`<db>.otel-flush.lock`) blocks for the whole flush. With a slow or hanging collector, a burst of `Stop` events queued one blocked `rtok otel flush` process per event, unbounded. Checked the HTTP side too: `flush_into`'s `reqwest::Client` already sets `.timeout(flush_secs)` (documented in `config/default.toml` as "proxy / mcp flush interval, and the POST timeout"), so a hung collector was already bounded — confirmed with a new unit test against a listener that accepts and never answers; no timeout fix was needed.

Fix (coalescing, at most one running + one queued hook-spawned flush): a second lock file `<db>.otel-flush-queued.lock`. `spawn_child` now does a cheap non-blocking pre-check (`queued_lock_held`) and skips spawning entirely if another hook-spawned flush is already queued — it will post whatever this event wrote. The spawned child runs `rtok otel flush --coalesce` (a hidden clap flag), which claims the queued slot non-blocking (`try_queue`); if already claimed it exits at once (`Report::default()`); otherwise it waits for the (blocking) flush lock, releases the queued slot as soon as it holds the flush lock (so a new hook-spawned flush can start queuing behind it), then flushes normally (`flush_coalesced` / `flush_coalesced_blocking` in `src/otel/export.rs`, sharing `run_flush` with the existing `flush`). A manual `rtok otel flush` (no `--coalesce`) never consults the queued lock and always flushes, as before.

Check: `tests/otel.rs::hook_spawned_flushes_coalesce_to_at_most_two_processes` reproduces the pile-up against a delayed mock collector — fires 20 real `rtok hook Stop` subprocesses and counts concurrently alive flush children via a trace directory each one marks with `<pid>.run` for its own lifetime (`RTOK_OTEL_FLUSH_TRACE`, read by `FlushTrace` in `src/otel/export.rs`; test-only, no host process table query — no `ps`, no `kill`, ever); failed on unfixed code with "at most 2 hook-spawned flush processes may be alive at once, saw 20", passes after the fix (max 2), and confirms every seeded row posts exactly once (no loss, no duplicates), waiting bounded for the trace dir to empty on its own rather than killing anything. `manual_flush_ignores_the_queued_slot` and `hook_skips_spawning_when_a_flush_is_already_queued` (warm-up call absorbs the freshly linked binary's one-time first-exec cost, matching `hooks_stay_fast_with_an_unreachable_endpoint`'s load-aware approach; asserts the trace dir stays empty) cover the two documented behaviours. Unit tests in `src/otel/export.rs` cover the queued-lock primitive (first attempt wins, others back off, frees on drop, independent of the flush lock, lock file created next to the DB) and the hung-collector timeout. `hook_spawned_flushes_coalesce_to_at_most_two_processes` isolated in `.config/nextest.toml` (`threads-required = "num-test-threads"`) since a loaded box can genuinely push concurrency past the bound, not just skew a measurement. `just check` green: fmt, clippy (workspace + wasm-demo-guest), full nextest (bench overrides untouched). `--coalesce` is `hide = true` but still shows in the AOT shell completions (bash/fish/zsh; PowerShell unaffected) — a pre-existing `clap_complete` 4.6.11 limitation, not something this change introduced: its AOT generators (`src/aot/shells/{bash,fish,zsh}.rs`) only filter hidden `PossibleValue`s, never hidden args or subcommands, so already-hidden commands like `demon upgrade` show the same way in the same snapshots. `cli_trycmd` left blessed with `--coalesce` visible for that reason.
