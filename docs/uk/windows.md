# Розробка rtok на Windows

Що поводиться інакше, ніж за контрактом CI, коли `just check` запускається на
машині з Windows, і що робити з кожною відмінністю. Виявлено 2026-09-26 під час першого
локального запуску повної перевірки на Windows (T272–T274).

## Windows-завдання в CI запускає лише тести

Матриця `windows` у `ci.yml` запускає `cargo nextest run --workspace` (у двох
шардах); `fmt`, `clippy`, `dup`, `js` і `python` живуть у Linux-завданнях.
Тому локальний `just check` на Windows суворіший за те, що CI доводить
щодо Windows, і він виявляє борг лінтингу, специфічний для Windows, якого Linux-завдання лінтингу
не бачать: код за `#[cfg(windows)]` або `#[cfg(unix)]` аналізується лише
на тій ОС, яка його компілює. T273 (`permissions_set_readonly_false`
у `cfg(windows)` `clear_readonly`) і T274 (тестовий код у Unix-стилі:
тіла з раннім поверненням, допоміжні функції лише для unix) належали саме до цього класу. Якщо clippy
падає на Windows через код, який CI ніколи так не лінтить, виправте його — не додавайте
`--allow` до рецепта.

## Закінчення рядків: як у checkout у CI

Git for Windows типово використовує `core.autocrlf=true`, що робить checkout дерева
з CRLF. Golden-тести порівнюють із байтами фікстур (`tests/cmd_golden/*.in`)
і падають на дереві з CRLF — `apt.in` видавав `ok 0\r\n` там, де очікувалося
`ok 0\n`. Ранери CI роблять checkout з LF. Вирівняйте дерево:

```bash
git config core.autocrlf false
git rm --cached -r . && git reset --hard HEAD
```

Вміст репозиторію — LF; це лише переписує робоче дерево до того стану, який бачить CI.

## dart у PATH змушує один тест запуститися — і впасти

`graph_lsp_gate::lsp_backend_outlines_dart_main` пропускається, коли `dart` немає в
PATH, тож CI ніколи його не запускає. На машині зі встановленим Dart SDK він запускається,
і на Windows dart 3.9 сервер аналізу відповідає
`File is not being analyzed` для щойно записаного тимчасового проєкту — виклик
outline падає ще до перевірок. Доки це не виправлено (дорожня карта,
досвід розробника на Windows), виключайте його локально:

```bash
mise exec -- cargo nextest run --workspace -E 'not test(lsp_backend_outlines_dart_main)'
```

## Антивірус повільно «розігрівається» на свіжих бінарниках

Після перезбирання всього дерева (а саме його спричиняє вирівнювання CRLF вище)
Defender глибоко сканує кожен щойно записаний `rtok.exe`/тестовий бінарник під час першого
запуску. Тести `agents_install` запускають бінарник багато разів і можуть упертися
в 181 с `terminate-after` у nextest, поки все «холодне», — ті самі тести проходять під час
повторного «теплого» запуску. Якщо два інтеграційні тести вичерпують час одразу після великого перезбирання,
перезапустіть їх, перш ніж розбиратися; виключення `target\` зі сканування в реальному часі
повністю прибирає цей ефект (це рішення на рівні машини, а не репозиторію).

## Інструментарій

Усе надходить через mise; `pipx:pytest` розв'язується на Windows лише за наявності
`uv` (закріпленого в `mise.toml` — бекенд pipx не має збірки для Windows
у реєстрі mise). Запускайте cargo як `mise exec -- cargo <cmd>`, ніколи не через
системний інструментарій (CONTRIBUTING.md).
