# Маршрутизація моделей (D9)

**Статус: заплановано / Пізніше** — не типовий шлях v0.1. Лише заглушка конфігурації й
документація, доки не з'явиться Check вимірювання. **Окремий напрям роботи, відмінний від
Batch і Flex** (`docs/batch-flex.md`): вони змінюють те, *як* або *коли* за
запит виставляється рахунок на тому самому (або асинхронному) інтерфейсі; маршрутизація моделей змінює те,
*який* рядок `model` передають далі синхронні чат-протоколи.

Джерело задуму: рішення **D9** у `plan.md`, варіант
**#3** у `research.md` §16.3 (і sticky-upstream #1 / I-84), беклог економії токенів I-101 в `ideas.md`.
Поведінка, яку не підключено в `src/proxy/`, позначено як **заплановано**.

## Що це

D9 (*Агенти не залежать від провайдера*): маршрутизувати за завданням — недорогі моделі для
механічної роботи, середній рівень для програмування, високопродуктивні для досліджень лише
після підтвердження користувача. Назви продуктів-хостів — не виконавець.

`research.md` §16.3 #3 (*Маршрутизація моделей / рівнів за завданням*):

- Дешева модель для форматування / класифікації / підготовки expand
- Середня для редагування
- Дорога лише після підтвердження
- Вплив переважно в **$** (мала зміна в сирих токенах)
- Потрібні **політика маршрутизатора + вимірювання**, щоб заявлена «економія» була в доларах,
  а не у відчуттях

Сьогодні rtok — це проміжний інтерфейс (хуки, MCP, API-проксі) і типово **не** є
маршрутизатором моделей. Модель і далі обирають агенти (або хост);
проксі залишає `model` таким, яким його надіслав клієнт.

## Як це працювало б у rtok

Лише в `rtok proxy` (`src/proxy/`), на **синхронних** чат-протоколах
(`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, Gemini
`:generateContent`). Хуки й MCP ніколи не бачать HTTP-тіл запитів до LLM, тож
не можуть реалізувати D9.

**Сьогодні**

- Одна URL-адреса upstream; `model` лишається таким, яким його надіслав клієнт
- Немає класифікатора; немає таблиці політик
- Прив'язка (sticky) до *pod/регіону upstream* (I-84 / §16.3 #1) стосується
  **влучань у кеш промптів**, а не вибору дешевшої моделі — лише пов'язаний прапорець
  конфігурації

**Заплановано** (після Check для D9)

1. Необов'язкова політика / класифікатор визначає цільову модель (або рівень) для цього
   ходу
2. `shape_request` → **prepare** може **переписати** поле JSON `model`
   у межах `[proxy.routing]`, коли `enabled = true`
3. Check вимірювання розподіляє $ до/після, щоб політика лишалася чесною
4. Форма таблиці політик / класифікатора: **ще не визначено** (**TODO**)

Жодного прозорого перетворення sync→Batch; маршрутизація не ставить Batch у чергу й не
задає Flex `service_tier`. Вони лишаються в `[proxy.batch]` / `[proxy.flex]`.

## Конфігурація (заплановано — бінарник її ще не завантажує)

Невідомі ключі не проходять `rtok config validate`, доки не з'являться поля `Config`.
Та сама заглушка, що й у `docs/batch-flex.md`:

```toml
# Заплановано — сьогодні не розбирається
[proxy.routing]
enabled = false         # маршрутизація моделей / рівнів (D9); вимкнено, доки немає політики + Check
sticky = true           # віддавати перевагу одному upstream заради прив'язки кешу промптів (I-84)
default_model = ""      # порожньо = лишити модель клієнта
# таблиця політик / класифікатор: ще не визначено (**TODO**)
```

MVP для Batch/Flex може розбирати це **лише як заглушку** (`enabled = false`,
без переписування). Повна політика + класифікатор — це окремий подальший план (див. дорожню карту
S6 / T256), а не частина критеріїв готовності Batch/Flex.
