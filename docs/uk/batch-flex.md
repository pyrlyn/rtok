# Batch, Flex і маршрутизація

rtok — це проміжний інтерфейс (хуки, MCP, API-проксі), а не агент і типово не
маршрутизатор моделей. **Batch**, **Flex** і **маршрутизація моделей** — це три
різні важелі вартості. Ця сторінка фіксує, що проксі робить сьогодні, що
**заплановано** і як кожен із них взаємодіє з кешуванням промптів.

Джерело задуму: `ideas.md` (нотатки про економію токенів I-100/I-101), `docs/prompt-cache.md`,
`research.md` (sticky-маршрутизація / D9). Поведінка, яку не підключено в
`src/proxy/`, позначено як **заплановано**.

## Три різні речі

| Важіль | Що це | Синхронний хід агента? | Переписує тіло? |
|-------|------------|------------------|--------------------|
| **Batch** | Асинхронні API провайдерів (`/v1/batches`, `/v1/messages/batches`, …) | Ні — надіслати, опитувати, забрати результати | **Pass-through** (без перетворення sync→Batch) |
| **Flex** | Ті самі синхронні endpoint, дешевший/повільніший рівень через `service_tier` | Так | **Переписування** в `prepare` (`[proxy.lanes.<lane>] flex`) |
| **Маршрутизація моделей** | Обрати дешевшу модель для простих ходів (D9) | Так | **Переписування** `model` лише для викликів `internal` і ввімкненого `bulk` (`[proxy.routing]`) |

rtok **не** перетворює прозоро живий `POST /v1/messages` агента (або
`/v1/chat/completions`) на завдання Batch. Агентам потрібна синхронна відповідь на
той самий HTTP-запит; Batch — це окремий клієнтський процес, який лише проходить
через той самий вузол проксі.

Інструменти MCP і хуки Claude Code ніколи не бачать HTTP-трафіку до LLM — його бачить лише проксі.
Тому Batch/Flex/маршрутизація цілком живуть у `rtok proxy`
(`src/proxy/`), а не в `src/hooks/` чи `src/mcp.rs`.

## Pass-through проти переписування

Конвеєр проксі для не простого запиту (`shape_request` у `src/proxy/mod.rs`):

1. **record** — рядки `calls` / `call_io` (fail-open)
2. **compress** — лише коли `proxy.mode = "compress"`; виконує `Plugin::proxy_filter`
3. **tools_rewrite** — вмикається явно через `[proxy.tools_rewrite]`
4. **prepare** — формування запиту під конкретний протокол: OpenAI
   `stream_options.include_usage`, бета context-management в Anthropic, коли її активовано,
   і OpenAI `service_tier` на смузі з `flex`
5. пересилання в upstream; дублювання відповіді для розбору використання, коли збігається `Wire`

Невідомі шляхи й далі потрапляють у **fallback** axum і пересилаються побайтово ідентичними
до upstream провайдера. `Wire::matches` точно збігається з формами синхронного чату
(`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, Gemini
`:generateContent`). Шляхи Batch **не** збігаються з жодним протоколом, тож вони пропускають
compress, prepare і синхронний розбір використання. Їх усе одно класифіковано
(`calls.kind = api_request:batch`) і переслано без змін.

| Клас шляхів | Поведінка |
|------------|-----------|
| Синхронні чат-протоколи | record + необов'язкові compress/prepare + використання |
| Endpoint Batch | пересилання через fallback; без `Wire`; тіло без змін; тег `api_request:batch`. `[proxy.batch] parse_results` пише `usage` з пересланого файлу результатів |
| Flex (`service_tier`) | клієнтське значення зберігається; `prepare` задає `flex` лише у ввімкнених смугах і перезаписує його лише за `[proxy.flex] force` |
| Маршрутизація моделей | `[proxy.routing]` переписує `model` лише у викликах `internal` і ввімкненого `bulk`; смуга `agent` не маршрутизується |

## Endpoint Batch API

Batch провайдера — це асинхронний API, **який ініціює клієнт**. Спрямуйте ту саму базову URL-адресу на
`rtok proxy`; fallback пересилає шлях.

### OpenAI

| Метод | Шлях | Роль |
|--------|------|------|
| `POST` | `/v1/batches` | створити пакет із завантаженого файлу JSONL |
| `GET` | `/v1/batches/{id}` | опитати статус |
| `GET` | `/v1/batches` | перелік |
| `POST` | `/v1/batches/{id}/cancel` | скасувати |
| (файли) | `/v1/files` | завантажити вхідні дані / забрати вихідні (теж пересилається через fallback) |

Підтримувані endpoint для елементів пакета (документація провайдера): `/v1/chat/completions`,
`/v1/responses`, `/v1/embeddings` та інші. rtok не переписує рядки JSONL
усередині файлу пакета.

### Anthropic

| Метод | Шлях | Роль |
|--------|------|------|
| `POST` | `/v1/messages/batches` | створити Message Batch |
| `GET` | `/v1/messages/batches/{id}` | опитати |
| `GET` | `/v1/messages/batches` | перелік |
| `GET` | `/v1/messages/batches/{id}/results` | отримати результати потоком / завантажити |
| `DELETE` | `/v1/messages/batches/{id}` | видалити (після скасування, якщо виконується) |

Точний збіг із `/v1/messages` означає, що `/v1/messages/batches…` ніколи не потрапляє
до адаптера `Wire` для Anthropic — жодного `proxy_filter`, жодного вставлення context-management.

### Чим Batch **не** є

- Не заміна Flex для живого ходу агента.
- Не автоматичний: rtok ніколи не ставить живий хід агента в чергу Batch. `rtok batch` —
  окремий клієнт API Batch провайдера, а не перетворювач.
- Не видимий для хуків/MCP.

### CLI (вмикається явно)

Тонкий інтерфейс, **що вмикається явно**, для людей/скриптів, які вже працюють із Batch провайдера, —
поза циклом агента. Він **не** замінює `ANTHROPIC_BASE_URL` /
`OPENAI_BASE_URL` агента (вони лишаються на синхронних чат-протоколах). Команди звертаються до того самого
вузла `rtok proxy` (`--url`, за замовчуванням `[proxy] bind` і `port`) і **пропускають без змін**
шляхи Batch провайдера (`/v1/batches`, `/v1/messages/batches`, …); жодного перетворення sync→Batch.

| Команда | Роль |
|---------|------|
| `rtok batch submit <jsonl>` | створити пакет із файлу, де на рядок припадає один запит у форматі провайдера |
| `rtok batch status <id>` | об'єкт пакета, як його віддає провайдер |
| `rtok batch fetch <id> <out>` | результати в новий файл `<out>` (наявний файл не перезаписується) |

- Ключ читається лише з `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`; провайдер — `--provider`, інакше
  визначається за id (`msgbatch_…` — Anthropic).
- Anthropic: кожен рядок — `{custom_id, params}`, рядки йдуть у `requests` байт у байт. OpenAI:
  кожен рядок — `{custom_id, method, url, body}`; файл завантажується з `purpose=batch`, потім
  створюється пакет для єдиного `url`, спільного для рядків (`completion_window` `24h`); `fetch`
  іде за `output_file_id`.
- Шляхи OpenAI `/v1/batches*` і `/v1/files*` не мають `Wire`; проксі надсилає їх до
  `proxy.openai_upstream` (запит з `anthropic-version` — це Files API Anthropic, він лишається на
  `proxy.upstream`).

Див. також `ideas.md` (беклог економії токенів I-100/I-101).

## Flex API (синхронний, дешевший рівень)

Обробка Flex в OpenAI — це той самий HTTP-інтерфейс Chat Completions / Responses
з `"service_tier": "flex"` (документація провайдера). Затримка вища, ціна
нижча; кешування промптів може діяти й на цьому рівні, якщо провайдер це
підтримує.

**Сьогодні:** якщо клієнт уже надсилає `service_tier`, проксі пересилає його
без змін (passthrough / compress не вирізають невідомі поля на шляху розбору протоколу,
який повторно серіалізує тіло лише після того, як фільтр його змінить).

**Flex по смугах:** `[proxy.lanes.<lane>] flex = true` (смуги `bulk`, `internal`, `embeddings`, `meta`;
ніколи `agent`) дозволяє `prepare` задати `service_tier = "flex"` у двох протоколах OpenAI, а `[proxy.flex]`
налаштовує поведінку:

- поле додається, якщо клієнт його не вказав (або надіслав `null`); решта байтів пересилається як є
- клієнтські `"default"` / `"auto"` / `"priority"` / `"flex"` поважаються; `force = true` їх перезаписує
- за `429 Resource Unavailable` (нічого не списується, за настановою OpenAI від 2026-10-08) вирішує
  `on_429`: `none` віддає помилку клієнту, `backoff` повторює на Flex із подвоюваними паузами,
  `default` повторює один раз із рівнем клієнта, якщо `force` його замінив, інакше з `auto`.
  `Retry-After` у секундах подовжує паузу (максимум 30 с); `408` не повторюється. Повторюється лише рівень, заданий rtok.

Ключі й типові значення: [config.md](config.md#proxyflex).

В Anthropic немає аналога `service_tier`; Flex тут означає OpenAI (і будь-якого майбутнього
провайдера, який надасть еквівалентне поле у `Wire`).

## Взаємодія з кешем

Див. також [prompt-cache.md](prompt-cache.md).

| Механізм | Batch | Flex | Примітки |
|-----------|-------|------|-------|
| **Кеш промптів** провайдера (точний префікс) | Залежить від провайдера; OpenAI документує поєднання Flex і кешу; рядки JSONL у Batch — окремі запити | Ті самі правила префікса, що й для синхронних; sticky upstream і далі важливий | rtok не має змінювати `system` / `tools` / живі ходи — для синхронного compress це вже так |
| Переписування живої зони **архівом** rtok | Не застосовується до створення Batch (немає `Wire` Messages) | Те саме, що й для синхронних, коли Flex іде через Chat/Responses | Тіла елементів пакета всередині файлу не переписуються |
| **Семантичний** кеш відповідей (P31) | Вимкнений для створення/опитування Batch: політика смуги `batch` лишає `semantic_cache` хибним, і смуга проходить наскрізь | Ті самі правила придатності, що й для синхронних | Влучання однаково дає агентам неправильну відповідь |

Sticky-маршрутизація (закріплення того самого pod/регіону upstream за сесією) стосується
**влучань у кеш промптів**, а не Batch проти Flex. Завдання Batch асинхронні й зазвичай
не можуть ділити живий KV сесії з інтерактивним агентом; не розраховуйте отримати
і знижку Batch, **і** частку читання з кешу інтерактивної сесії на тих самих
байтах.

## Вимірювання / метрики

**Сьогодні (синхронні протоколи):** кожен запит через проксі може записувати `calls`, `call_io`,
`tokens` і `usage` (чотири лічильники). `rtok stats` / `rtok stats --price`
читають ці рядки. Шляхи без `Wire` (Batch, `/v1/models`, …) записують
виклик, коли облік увімкнено, але пропускають синхронний розбір використання (`src/proxy/mod.rs`).
Файл результатів Batch — виняток, коли ввімкнено `[proxy.batch] parse_results`, нижче.

**Смуги (T385.1):** кожен запит класифікується в смугу (`src/proxy/lane.rs`), і її записує
`calls.kind`: `api_request` для `agent`, `api_request:<lane>` для `bulk`, `batch`, `files`,
`embeddings`, `meta` і `internal`. Шлях визначає Batch, files, embeddings і meta;
`x-rtok-lane` або префікс `/lane/<name>/` вибирає `bulk` або `internal` для синхронного
чат-виклику. Обидва вилучаються перед пересиланням. Див. `[proxy.lanes]` у
[config.md](config.md).

**Журнал Batch:**

- `calls.kind` позначає створення, опитування і результати Batch як `api_request:batch`, окремо від
  синхронного `api_request` (T385.1)
- `[proxy.batch] parse_results` пише порядковий `usage` з пересланого файлу результатів (T385.4);
  `rtok stats --price` оцінює це використання за рядком `<model>@batch` у `[stats.prices]` (T385.12.1)
- `rtok stats` друкує таблицю `lane/tier`, а `rtok report` показує ті самі рядки в розділі Cache
  (T385.12.2)

**Журнал Flex:**

- `calls.service_tier` — рівень, який назвала відповідь, а не запит (T385.12.2)
- `stats --price` відносить використання рівня `flex` до `<model>@flex` (в OpenAI Flex коштує за ставками Batch)

Економія й далі потребує рядка `Measurement`. Ці рядки журналу — лічильники й оцінене використання;
вони не стверджують, що Flex або Batch зекономили токени в конкретній сесії.

## Конфігурація

Ключі нижче завантажуються. Типові значення, діапазони й перевірка — у [config.md](config.md).
`sticky` ключем не є: прив'язка кешу промптів (I-84) і далі запланована.

```toml
[proxy.batch]
parse_results = false   # рядки usage з пересланого файлу результатів; тіло лишається побайтово тим самим

[proxy.lanes.bulk]
flex = true             # які смуги можуть задавати service_tier; у agent, batch і files перемикача flex немає

[proxy.flex]
force = false           # перезаписати service_tier клієнта
on_429 = "none"         # none | backoff | default
retries = 3             # лише backoff
backoff_ms = 1000       # лише backoff

[proxy.routing]
enabled = false         # маршрутизація моделей викликів internal / bulk; типово вимкнено
```


## Маршрутизація моделей (окремий напрям)

**За ввімкненням, лише смуги `internal` і `bulk`** — не частина MVP Batch/Flex. Рішення **D9** /
`research.md` §16.3 #3: маршрутизація за завданням через переписування `model` у `[proxy.routing]`.
Смуга `agent` не маршрутизується ніколи (маршрутизація ходів агента лишається Later, за контролем
якості I-101). Sticky upstream (`sticky`, I-84, поки заплановано) — це прив'язка кешу промптів,
а не вибір моделі. Повний дизайн: [model-routing.md](model-routing.md).
