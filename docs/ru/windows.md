# Разработка rtok в Windows

Что ведёт себя иначе, чем в контракте CI, когда `just check` запускается на
машине с Windows, и что с каждым из этих случаев делать. Обнаружено 2026-09-26 при первом полном
локальном прогоне проверок в Windows (T272–T274).

## Задание CI для Windows запускает только тесты

Матрица `windows` в `ci.yml` запускает `cargo nextest run --workspace` (в двух
шардах); `fmt`, `clippy`, `dup`, `js` и `python` выполняются в заданиях Linux.
Поэтому локальный `just check` в Windows строже, чем то, что CI доказывает
о Windows, и он выявляет долг линтинга, специфичный для Windows, который задания линтинга в Linux
не видят: код за `#[cfg(windows)]` или `#[cfg(unix)]` анализируется только
на той ОС, которая его компилирует. T273 (`permissions_set_readonly_false`
в `clear_readonly` под `cfg(windows)`) и T274 (тестовый код в духе unix:
тела с ранним возвратом, хелперы только для unix) были как раз из этого класса. Если clippy
падает в Windows на коде, который CI так никогда не линтит, исправьте его — не добавляйте
`--allow` в рецепт.

## Концы строк: как в checkout CI

Git для Windows по умолчанию использует `core.autocrlf=true`, из-за чего дерево извлекается
с CRLF. Golden-тесты сравнивают с байтами фикстур (`tests/cmd_golden/*.in`)
и падают на дереве с CRLF — `apt.in` выдал `ok 0\r\n` там, где ожидалось `ok 0\n`.
Раннеры CI извлекают LF. Выровняйте дерево:

```bash
git config core.autocrlf false
git rm --cached -r . && git reset --hard HEAD
```

Содержимое репозитория — LF; это лишь переписывает рабочее дерево так, как его видит CI.

## dart в PATH заставляет один тест запуститься — и упасть

`graph_lsp_gate::lsp_backend_outlines_dart_main` пропускается, когда `dart` нет в
PATH, поэтому CI его никогда не запускает. На машине с установленным Dart SDK он запускается,
и в Windows с dart 3.9 сервер анализа отвечает
`File is not being analyzed` для только что записанного временного проекта — вызов outline
падает раньше проверок. Пока это не исправлено (дорожная карта, опыт разработки
в Windows), исключите его локально:

```bash
mise exec -- cargo nextest run --workspace -E 'not test(lsp_backend_outlines_dart_main)'
```

## Антивирус медленно «прогревается» на свежих бинарниках

После пересборки всего дерева (а именно её вызывает выравнивание CRLF выше)
Defender глубоко сканирует каждый только что записанный `rtok.exe`/тестовый бинарник при первом
запуске. Тесты `agents_install` запускают бинарник много раз и в холодном состоянии могут упереться
в `terminate-after` nextest в 181 с — те же тесты проходят при
тёплом перезапуске. Если два интеграционных теста завершаются по таймауту сразу после большой пересборки,
перезапустите их, прежде чем разбираться; исключение `target\` из сканирования в реальном времени
полностью убирает этот эффект (решение на уровне машины, а не репозитория).

## Тулчейн

Всё ставится через mise; `pipx:pytest` разрешается в Windows только при наличии
`uv` (закреплён в `mise.toml` — у бэкенда pipx нет сборки для Windows
в реестре mise). Запускайте cargo как `mise exec -- cargo <cmd>`, а не через
системный тулчейн (CONTRIBUTING.md).
