# Маршрутизация моделей (D9)

**Статус: запланировано / Later** — это не путь по умолчанию в v0.1. Пока нет проверки
измерением, есть только заготовка конфигурации и документация. **Это отдельное направление работы, не связанное с
Batch и Flex** (`docs/batch-flex.md`): они меняют то, *как* или *когда*
запрос тарифицируется на том же (или асинхронном) интерфейсе; маршрутизация моделей меняет то,
*какую* строку `model` передают дальше синхронные чат-протоколы.

Источник замысла: решение **D9** в `plan.md`, вариант
**#3** в `research.md` §16.3 (а также sticky upstream #1 / I-84), бэклог экономии токенов I-101 в `ideas.md`.
Поведение, которое не подключено в `src/proxy/`, помечено как **запланировано**.

## Что это такое

D9 (*Agents are provider-agnostic*): маршрутизация по задаче — недорогие модели для
механической работы, средний уровень для написания кода, высокопроизводительные для исследований только
после подтверждения пользователем. Названия продуктов-хостов не определяют реализацию.

`research.md` §16.3 #3 (*Model / tier routing by job*):

- Дешёвая модель для форматирования / классификации / подготовки к expand
- Средняя для редактирования
- Дорогая только после подтверждения
- Эффект в основном в **$** (сырое количество токенов меняется мало)
- Нужны **политика маршрутизатора + измерение**, чтобы заявленная «экономия» была в долларах,
  а не в ощущениях

rtok сегодня — это промежуточный слой (хуки, MCP, API-прокси), а **не**
маршрутизатор моделей по умолчанию. Модель по-прежнему выбирают агенты (или хост);
прокси оставляет `model` таким, каким его отправил клиент.

## Как это работало бы в rtok

Только в `rtok proxy` (`src/proxy/`), на **синхронных** чат-протоколах
(`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, Gemini
`:generateContent`). Хуки и MCP никогда не видят HTTP-тела запросов к LLM, поэтому
не могут реализовать D9.

**Сегодня**

- Один URL upstream; `model` остаётся таким, каким его отправил клиент
- Нет классификатора, нет таблицы политик
- Привязка к *поду/региону upstream* (sticky, I-84 / §16.3 #1) нужна для
  **попаданий в кеш промпта**, а не для выбора более дешёвой модели — есть только
  связанный флаг конфигурации

**Запланировано** (после проверки D9)

1. Необязательная политика / классификатор выбирает целевую модель (или уровень) для этого
   хода
2. `shape_request` → **prepare** может **переписать** поле JSON `model`
   в `[proxy.routing]`, когда `enabled = true`
3. Проверка измерением относит $ до/после, чтобы политика оставалась честной
4. Форма таблицы политик / классификатора: **пока не определена** (**TODO**)

Никакого прозрачного преобразования sync→Batch; маршрутизация не ставит запросы в очередь Batch и не
задаёт `service_tier` для Flex. Это остаётся в `[proxy.batch]` / `[proxy.flex]`.

## Конфигурация (запланировано — бинарник её пока не загружает)

Неизвестные ключи не проходят `rtok config validate`, пока не появятся поля `Config`.
Та же заготовка, что и в `docs/batch-flex.md`:

```toml
# Запланировано — сегодня не разбирается
[proxy.routing]
enabled = false         # маршрутизация моделей / уровней (D9); выключено, пока нет политики + проверки
sticky = true           # предпочитать один upstream ради привязки к кешу промпта (I-84)
default_model = ""      # пусто = оставить модель клиента
# таблица политик / классификатор: пока не определены (**TODO**)
```

MVP для Batch/Flex может разбирать это **только как заготовку** (`enabled = false`,
без переписывания). Полная политика + классификатор — это последующий план (см. дорожную карту,
S6 / T256), и он не входит в критерии готовности Batch/Flex.
